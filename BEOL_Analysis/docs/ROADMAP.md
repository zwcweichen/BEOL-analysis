# BEOL 分析戰報：開發路線討論（2026-10-09）

> 立場：以製程整合主管加上系統開發者的角度，審視兩個延伸方向——知識庫維護、機台 commonality 與多檔連動——並提出設計、風險與優先順序。
> 現況：v2.2。點燈表與 trend 已具公版性質；產品特色在「異常 item 的診斷與建議檢查」。

---

## 1. 知識庫（rules.js）的維護

### 1.1 現況
- `R.CATS` 本質上已經是**資料**而不是程式：每個類別是 {名稱 regex、單位 regex、偏高／偏低的意義、原因、檢查、配對 inline 與方向}。
- 只有兩個地方需要「程式」：欄名 regex、層別代號的解析。這是非程式背景使用者的門檻。

### 1.2 方案 a：論文（arXiv 等）作為來源 — 建議降為輔助
- fab 等級的診斷規則（Rc 偏高 → via 底部殘留、barrier 偏厚；Rs 偏高 → CMP 過拋）是**經驗知識**，來源是 FA 報告、8D、OCAP、過去的 HL 結案紀錄，不是論文。arXiv 上 BEOL 整合的內容很少，多半是材料與元件物理。
- 論文的價值在「機制解釋」與「參考文獻」（例如 Cu 線寬縮小的電阻率上升、EM 與 barrier 的關係），可以讓診斷文字多一句「依據」，但不會產生檢查清單。
- fab 內電腦通常離線，工具本身不能連網。
- **建議**：把論文來源放在工具**外**的流程：由 Claude（在能連網的環境）讀論文或 FA 報告，依「規則公版」草擬規則，附來源；工程師審核後匯入。這樣 agent 的角色是「知識庫編輯助理」，工具維持確定性、離線、可審查。

### 1.3 方案 b：文字敘述 → 規則 — 建議「公版 + 編輯器」而不是自由翻譯
自由文字翻譯成規則的問題不是難度，而是**錯了不知道**：規則寫錯會讓某個欄位永遠不配對，或配對到錯的層，而且不會報錯。

建議的做法分三層：

| 層 | 內容 | 誰維護 |
|---|---|---|
| 公版（schema） | 固定欄位：類別、kind（WAT／inline）、指標（k／fold／rate）、欄名樣式、單位、偏高意義、偏高原因、偏高檢查、偏低意義、偏低原因、偏低檢查、配對類別、方向 | 開發者 |
| 基礎層 | 隨工具出貨的物理知識（目前的 rules.js 內容） | 開發者 |
| fab 層 | 使用者新增或覆寫的規則，存成一份 `rules.json`（或 Excel 一個 sheet，一列一條規則） | 工程師 |

關鍵設計：
1. **欄名樣式用萬用字元，不用 regex**：`Con_*`、`LK_*`、`*_CD_AEI`。程式轉成 regex。層別代號維持內建解析，使用者只需填「層別來自欄名」。
2. **工具內建「知識庫」頁**：表格編輯（新增、修改、停用），匯入／匯出 JSON 與 Excel，並有**試算**：載入規則後立刻顯示「目前資料中哪些欄位會命中這條規則」。沒有命中或命中錯欄位，當場看得到。
3. **版本與來源**：每條規則有作者、日期、來源（FA 編號、論文、經驗）。戰報頁尾印出知識庫版本，結論可追溯。
4. **分享方式要想清楚**：單一 HTML 在 `file://` 下不能自動讀旁邊的 JSON，`localStorage` 只在那台電腦的那個瀏覽器。所以：
   - 建置時把 `rules.json` 嵌進 HTML（`build.py` 已有 INLINE 機制），這是團隊共用的版本；
   - 執行時可用「載入知識庫檔」覆蓋，並存進 localStorage；
   - 「匯出知識庫」產生檔案，交給維護者合併回 `rules.json` 再重建 HTML。
5. **用 Claude 當草稿工具**：工程師用口語描述（「M12 的 LK 變大通常是 CMP 後殘留或 low-k 損傷，請先看 M12 CD 跟 post-CMP 缺陷」），Claude 依公版產出 JSON 片段；匯入時仍要過「試算」。這一步在工具外做，不需要工具連網。

### 1.4 比論文更有價值的來源：結案回饋
- 在 HL 詳細面板加一個「結案」欄位：實際原因（從建議清單選，或自填）、處置、日期。匯出成 CSV 累積。
- 累積後可以算每條規則的**命中率**（建議檢查第幾項最常是真因），之後排序建議順序、淘汰沒用的規則。這才是 fab 自己的知識庫在成長。

## 2. 機台 commonality 與多檔連動

### 2.1 先用零開發的方式驗證需求
- 工具現在就把**所有文字欄**當成可選的「分組欄」。使用者用 Excel VLOOKUP 把機台欄位貼進同一份資料後，選「分組欄 = TM1_CMP_Tool」，點燈表立刻變成每台機台一欄的 K。範例資料 `BEOL_horizontal_by_wafer.xlsx` 已經含 `TM1_CMP_Tool`、`TV1_ETCH_CH`。
- 這代表 commonality 的第一步不是資料連動，而是**自動掃描**：對每個異常 item，把資料中所有類別欄（機台、chamber、route、lot）逐一當因子做檢定，排序出最能解釋偏移的因子。

### 2.2 自動掃描（commonality engine）設計
- 範圍：只對異常 item，只在 CIP 內（或 CIP 加 BSL）。
- 每個類別欄：各組的 N、mean、與整體的偏移（以 BSL σ 表示）、Kruskal–Wallis 或 ANOVA 的 p 值、效果量（η²）。
- 排序：效果量優先，p 值次之；每組 N < 5 的因子降權或標示。
- 輸出：「疑似因子排名」表加上該 item 依因子分組的 box／strip plot（BSL 灰、CIP 彩色）。
- 這一段可以完全放進現有 HL 詳細面板，做為第三張圖與一個小表。

### 2.3 多檔連動（資料層）設計
使用者的想法方向正確：以 wafer id 為鍵，把不同時間匯入的檔案連起來，垂直格式先壓成 by wafer。補強以下幾點：

1. **鍵的正規化**：各系統的 wafer id 寫法不同——`UAB123.01`、`UAB123-01`、`UAB123#1`、lot 與 slot 分兩欄。要先建立標準鍵 `LOT.SS`（slot 補兩位），再連結。連結後**一定要顯示配對率**（「連結成功 96%，12 片找不到對應」），絕不能默默變成 0 筆。
2. **先聚合再連結**：垂直格式（一片多列）必須先壓成每片一列（mean／median，另存 site σ），再和機台表連。順序反了會讓機台表的列被複製，N 膨脹、K 失真。這是最容易出的 bug。
3. **機台履歷通常也是長表**：一列是「wafer × 站點 × 機台」。要先轉成寬表：每個站點變一欄，值是機台（或機台／chamber 複合）。rework 會讓同一站點出現兩列，預設取最後一次並標記。
4. **以 wafer 連結，不以時間連結**：WAT 時間與站點時間相差數週，時間對齊不可靠。
5. **混淆偵測**：commonality 最常見的錯誤結論——CIP 的 wafer 剛好全部走同一台機台，則「機台差異」與「條件差異」無法分辨。要做機台 × 條件的交叉表，退化時明確寫出「與條件完全混淆，無法判定是機台或條件」。
6. **多重比較**：30 個站點 × 20 個 item 會產生大量偶然顯著。用 Benjamini–Hochberg 校正，並要求效果量門檻，不只看 p 值。
7. **lot 效應**：現在的 K 把每片 wafer 當獨立樣本，lot 效應會讓顯著性膨脹。提供「以 lot 平均計算」的選項，至少在 HL 加註 lot 數。
8. **介面**：新增「資料層」面板：列出已匯入的來源、每個來源的鍵欄、配對率、wafer 的聯集與交集。匯入第二個檔案時由系統提議連結，使用者確認。

### 2.4 工程上的順序
- 先做 2.2（單檔內的自動掃描）：改動小、馬上可用，且驗證「使用者真的需要哪種 commonality 輸出」。
- 再做 2.3 的資料層：鍵正規化、配對率、長表轉寬表，是獨立的模組，和 importer／transform 同一層。

## 3. 其他值得納入的延伸

| 延伸 | 價值 | 成本 |
|---|---|---|
| 結案回饋與規則命中率（1.4） | 知識庫自己成長，也是產品的差異化 | 低 |
| 變化點偵測（CUSUM）：偏移從哪一天開始 | 直接對到機台保養、配方變更的日期 | 低～中 |
| 規格欄（USL／LSL）：超規比例與 Cpk | 使用者說規格常在欄位裡；點燈之外多一個客觀指標 | 低 |
| Yield 模組：bin ↔ WAT 對應 | 原本規劃；short bin ↔ LK／SPA，open bin ↔ Rc | 中 |
| 知識庫套件化：BEOL.json、FEOL.json | 同一個工具換知識庫就能做前段 | 低（公版做好之後） |
| 片內空間特徵（center／edge／notch 方位） | 對到 chamber 的特徵，補強 WIW 診斷 | 中 |

> 2026-10-09 更新：P1、P2 已完成（v2.3、v2.4）；v2.5 加入引導式建議檢查與機台分析視窗。**P3 結案回饋暫緩**（使用者決定先把分析與戰報產出、使用者體驗做好），列入後續。目前主線：使用者只提供資料就能得到點燈表、異常 item、可能原因、CP／WAT／inline 關係與 bad tool 判斷。

| 階段 | 內容 | 原因 |
|---|---|---|
| P1 | 規則公版 + 知識庫頁（編輯、試算、匯入匯出、版本）；單檔內類別欄自動掃描 | 兩者都在現有架構內，直接強化產品特色 |
| P2 | 資料層：wafer 鍵正規化、配對率、長表→寬表、混淆偵測；HL 面板加「疑似機台」 | 建立在 P1 的掃描之上 |
| P3 | 結案回饋與命中率；CUSUM；規格欄 | 讓知識庫和報告隨使用累積 |
| P4 | Yield 模組；知識庫套件化 | 擴大範圍 |
| 持續 | Claude 在工具外擔任知識庫編輯助理（論文、FA 報告 → 公版草稿） | 保持工具離線、確定性、可審查 |

### 需要使用者決定的事
1. 知識庫以 **JSON** 還是 **Excel** 為主要維護格式（建議兩者都支援，Excel 給工程師、JSON 給建置）。
2. 機台履歷的實際格式：一列一站點（長表）還是一列一片（寬表）？是否含 chamber、時間、rework？
3. CP／yield 資料格式（Yield 模組動工前）。
